## 结论

**本次改动是 bug fix, 不是性能优化。**
- 修复了 `KLU/UMFPACK/pypardiso` 失败一次后污染模块级缓存,导致后续所有 calc 永久回退 `scipy SuperLU` 的问题。
- 修复后:失败只影响当前 calc 实例, 其他实例仍可继续使用 KLU/UMFPACK。
- 异常捕获从 `Exception` 收窄到 `(RuntimeError, ValueError, ArithmeticError)`,避免吞掉无关 bug。
- 性能数据(端到端, 单进程, 平启动, 7 次测量取 min/med):
  - 8/8 算例均收敛, normF 数值前 4 位有效数字完全一致
  - 耗时差异在 ±5% 范围内, 本质是测量噪声, 与代码改动无关
- Windows 主机本底抖动约 ±10%, 本次对照下的差异(±5%)低于抖动水平。

**没有实现"大规模算例显著加速"** —— 主要原因:
1. 基线已使用 scipy SuperLU(C 库) 求解, 计算密度天花板低。
2. `SuperLU` 没有公开 `factor()` 方法 (KLU 才支持), 数值随迭代必须重分解。
3. KLU/UMFPACK/pypardiso 当前环境未装, 任何"换更高级求解器"的优化都无效。
4. Jacobian 构建占比 < 10%, 即使全部消除也只能减 < 5%。

如果想看大算例**真**显著加速,可行方向:
- **装 PyKLU**(`pip install pyklu`)并启用 numeric 复用(本仓库代码已预留 hook)
- **多进程并行**: `concurrent.futures` 跑 N 个算例, 墙钟时间 ≈ max/总时间 × N
- **Cython/C 改写热路径**: `_fill_standard_jacobian_data` 的 numpy 操作改 C 扩展
