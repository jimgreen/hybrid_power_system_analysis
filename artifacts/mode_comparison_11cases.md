## 总结

- **min 加速**算例(< -5%): 6/11
- **min 退化**算例(> +5%): 0/11
- **min 平均**: -14.7%
- **med 平均**: -10.7%
- **AC 最大加速**:ieee3w(30k 节点) min -43% / med -39%
- **AC ieee1w(10k 节点) min -34% / med -34%**
- **DC 30k 节点(dc_net_3w)**:min -2% / med +4% (基本无差异,Newton 求解主导)
- **Hybrid 80k 节点(qinling_1000) min -4% / med -1%**

## 结论

**`result_mode='array'` 对 AC 算例有显著加速效果(尤其大规模),对 DC/Hybrid 收益甚微。**

**AC 加速来源**:
- `full` 模式:Newton 收敛后要把 `V/theta` 写回 `ppc["bus"][:, 7/8]` 数组,
  并触发 `_write_ppc_result_to_network` 把数据写回 Python 对象网络 (Network/Bus/Branch/...)
- `array` 模式:**完全跳过** `network.writeback` 路径(`ACPowerFlowCalc._network_writeback=None`)
- AC 30k 节点时 Python 对象写回的开销远大于 Newton 迭代本身,故收益显著

**DC 收益接近 0**:`dc_net_3w` 30k 节点,full 与 array 几乎一样(4.28s vs 4.28s)。
原因是 DCPowerFlowCalc 求解后 `_write_back_ppc` 在 array 模式下被跳过,但**DC 本来就主要是数值计算**,
Newton 1 次迭代 7 个 SC SuperLU 求解就是 4s,Python 对象回填占比小。

**Hybrid 收益也小**:`qinling_1000` 80k 节点,加速仅 -4% min / -1% med。
原因是 `HybridPowerNetwork.read_from_file` + `prepare` 占了端到端 80%+ 时间,
Newton 迭代本身 0.6-0.9s,写回 0.2-0.3s,占比小。

**使用建议**:
- AC LF(尤其 ≥ 3k 节点):用 `array` 模式,加速 **-30% ~ -43%**
- DC LF / Hybrid LF:用 `array` 与 `full` 模式差异不大,按需选用
